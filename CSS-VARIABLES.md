# CSS variables guide

Roolith ships its design tokens as CSS custom properties. This guide covers how the token layer is built, which token to reach for, and how to change colour at build time or at runtime. [TOKENS.md](TOKENS.md) lists every token with its resolved light and dark value; it is generated by `npm run tokens` and is not edited by hand.

## How the pipeline works

Settings are compile-time inputs, custom properties are runtime outputs.

```
src/sass/_settings.scss           inputs: palette, accent roles, theme seeds and steps, component sizes
        |
        v
src/sass/_resolved.scss           the only derivation file: input validation, seed and step defaults, colour math, role maps
        |
        v
src/sass/_token-registry.scss     role to token names, per-theme component token values
src/sass/_token-emission.scss     mixins that emit each scope
src/sass/_token-check.scss        the build invariants, asserted when the module loads
        |
        v
src/sass/_css-variable.scss       the five rules and the shared component declarations
        |
        v
components                        read var(--r-*)
```

- `_settings.scss` is the input surface. Every entry is a `!default` value that only reuses other settings or a `rem()` call, so nothing in it derives colour, and any of it can be replaced with `@use 'roolith' with (...)`.
- `_resolved.scss` is the only file that derives colour values at build time. It merges the settings over built-in defaults, rejects unknown keys, validates the palette and the accent roles, computes the light and dark role maps, and derives each palette slot's text-safe colour.
- `_token-registry.scss` names the tokens. `$role-tokens` and `$private-role-tokens` map a derived role to its custom property name, and `$theme-component-tokens` holds the component token values for `light` and `dark`.
- `_token-emission.scss` holds the mixins that emit each scope: palette primitives, accent roles, surface scales, and the light and dark theme scopes.
- `_css-variable.scss` declares the five rules and the shared component declarations. It composes the emission mixins and lists the component tokens that are declared once, five of which blend with `color-mix()`. No component partial derives a theme role: derivation lives in `_resolved.scss`, and a component reads tokens, optionally blending one locally with `color-mix()`.
- `_token-check.scss` holds the build invariants, and `_css-variable.scss` imports it for their load-time effect: the two theme component token maps must list the same keys, every derived theme role must be registered, and every registered role must have a derived value.
- Components read `var(--r-*)`. Palette variant loops such as `.button-primary` go through `palette-fill()`, `palette-on()` and `palette-text()` with `resolved.$slot-roles`, so a scoped role override still recolours a variant.

`_css-variable.scss` declares four scopes plus one shared block, in this order:

1. `:root` - palette primitives. `--r-color-{slot}` and `--r-color-{slot}-on` do not change per theme, so they are declared once.
2. `:root, .theme-light` - the light scope: every theme role, the palette text pairs, the per-theme component tokens, and `color-scheme: light`.
3. `.theme-dark` - the dark scope: the same tokens with dark values, and `color-scheme: dark`.
4. `@media (prefers-color-scheme: dark) { :root:not(.theme-light) { ... } }` - the dark scope applied to the root element when the OS prefers dark and the root has not opted into `.theme-light`.
5. `:root, .theme-light, .theme-dark` - one shared block for tokens declared once because the declaration itself does not change per theme: accent roles, the internal surface scales, global, focus, animation, and component tokens that are built from other tokens.

Semantic roles are declared with their resolved literal in each theme scope instead of pointing at a private layer, so a theme class on any element switches that subtree without inheriting a stale value.

An excerpt of the emitted CSS, shortened to a few tokens per scope. The media block repeats the dark scope, so it is left out here.

```css
:root {
    --r-color-primary: #4a5cd0;
    --r-color-primary-on: #ffffff;
}

:root,
.theme-light {
    --r-surface-page: #ffffff;
    --r-text: #1e2128;
    color-scheme: light;
}

.theme-dark {
    --r-surface-page: #0c0c0c;
    --r-text: #a3a3a3;
    color-scheme: dark;
}

:root,
.theme-light,
.theme-dark {
    --r-accent: var(--r-color-primary);
    --r-focus-ring-color: var(--r-link);
}
```

A theme switch never rewrites a component rule to change a colour that a token already covers. `:root, .theme-light` and `.theme-dark` declare the same token names, so adding `.theme-dark` to `<html>` or to any container recolours that subtree, and removing it falls back to the light values. With no class at all the OS setting decides, and an explicit `.theme-light` wins over the media block because that block only matches `:root:not(.theme-light)`. Each theme scope also sets `color-scheme`, so native controls and scrollbars follow the active theme.

## The colour model

Palette primitives come from `$colors`. Each slot is emitted three times:

- `--r-color-{slot}` is the fill.
- `--r-color-{slot}-on` is the foreground pair from `$colors-on` for text and icons painted on that fill.
- `--r-color-{slot}-text` is the same colour made readable as text on a surface. It is derived per theme: the build walks the smallest blend toward black in light, or toward white in dark, that clears 4.5:1 against the page, the surface family, and the slot's own tint, measured with the WCAG contrast formula. A new slot needs two hand-picked colours, not three.

Accent roles come from `$accent-roles`, which aliases a role to a palette slot. Each role emits `--r-{role}`, `--r-{role}-on` and `--r-{role}-text` in the shared block. The defaults are `accent -> primary`, `danger -> danger`, `success -> success`, `warning -> info` and `info -> info`. Components read the role token, not the slot it points at.

Semantic tokens are the public roles derived in `_resolved.scss` from theme seeds and steps: surface (`--r-surface-page` through `--r-surface-control-hover`), text (`--r-text` and its tiers), border (`--r-border` and its tiers), and `--r-link`. They are the tier components use for meaning. `_token-check.scss` fails the build, through its import from `_css-variable.scss`, when a derived role is not registered as a token, or a registered token has no derived value.

Internal tokens use the `--_r-` prefix and are not part of the public API. They are the private theme roles that carry no semantic name (`--_r-on-surface`, `--_r-table-highlight`, `--_r-comment-highlight`, `--_r-radio-selected`, `--_r-loader-head`) and the surface scales (`--_r-surface-raised-step-*`, `--_r-surface-muted-step-*`), which are `color-mix()` blends between a surface and that theme's `on-surface` direction. The token layer builds component tokens from them; components never read them.

The surface scales are the depth mechanism. Values such as `--_r-surface-raised-step-10` are blends of a surface toward that theme's `on-surface` colour, and the token layer uses them for borders, dividers, tracks and hover fills that have to stay subtle in both themes. A component reads the public token built from a step, such as `--r-box-border-color` or `--r-table-border-color`, and never the step itself.

The contract is one boundary: `--r-*` is public, safe to read, and safe to override at runtime. `--_r-*` is internal and may change without notice.

## Choosing a variable

1. Use the semantic token for the meaning: `--r-text` for body copy, `--r-surface-raised` for a raised panel, `--r-border-control` for a field border.
2. Use a component token when the value belongs to that component and should stay tunable without touching component logic, such as `--r-card-background` or `--r-form-input-radius`.
3. Use palette primitives only for palette variants: `--r-color-{slot}` with its `-on` pair for filled variants, and the `-text` pair where the slot is the text colour. Inside SCSS variant loops, go through `palette-fill()`, `palette-on()` and `palette-text()` so a role override still applies.
4. Never read a `--_r-*` token from a component, and never hardcode a colour, radius or spacing that a token already covers.
5. Never add a `.theme-dark` colour rule in a component. The theme scopes already declare every themed token, so override the token locally when a narrow scope needs a different value. There are two exceptions, both in `_form.scss` and `_form-extended.scss`. The inline SVG icon rules are one, because those icons carry their colour inside the SVG data URI. The other is the `.theme-dark &:not([multiple]) option` rule in `.form-select`, which sets native `<option>` colours explicitly and therefore only applies under an explicit `.theme-dark` class, not under the `prefers-color-scheme` media query.

## Changing colour at build time

Colour settings stack from the palette up to direct role overrides. Each layer merges or replaces as noted, and each layer is validated.

1. `$colors` and `$colors-on` - the palette itself. `$colors` is replaced as a whole, so a swapped palette must keep the slots the framework reads, and `primary`, `link`, `secondary` and `tertiary` are required. Every slot needs a foreground pair; `$colors-on` merges over the built-in defaults, so list only the slots you change.
2. `$theme-light-seeds` and `$theme-dark-seeds` - the anchor colours a theme derives from: `page`, `surface`, `raised`, `muted`, `inverse`, `text`, `ink`, `link`, `hairline` and `on-surface`. They merge over the defaults. `$theme-dark-color` is the default dark `page` seed.
3. `$theme-light-steps` and `$theme-dark-steps` - the mix amounts applied to those anchors: `overlay`, `hover`, `control`, `control-hover`, the `border-*` and `text-*` steps, `table-highlight`, `table-lift`, `comment-highlight`, `comment-lift`, `radio-selected` and `loader-head`. They merge over the defaults, and a negative step blends the other way.
4. `$theme-light` and `$theme-dark` - direct overrides of the resolved role map, using the same role names, for example `surface-muted` or `border-control`. They merge over the derived map and are the last word for that theme.
5. `$accent-roles` - role to slot aliases, merged over the defaults.

```scss
@use 'roolith' with (
    $theme-dark-seeds: (page: #101014, raised: #1a1a20),
    $theme-light-steps: (border-control: 36%),
    $theme-light: (surface-muted: #f2f2f7),
    $accent-roles: (accent: link),
);
```

Unknown keys fail the build by design. That covers `$theme-light-seeds`, `$theme-dark-seeds`, `$theme-light-steps`, `$theme-dark-steps`, `$theme-light` and `$theme-dark`, so a typo cannot silently drop a token. The build also fails on a palette slot without a foreground pair, a missing required slot, an accent role pointing at a slot that does not exist, and two roles claiming one slot without a role named after it.

After a settings change, run `npm run tokens` to regenerate `TOKENS.md` and confirm the new values, or `node scripts/css-custom-properties.mjs --report` to see light and dark counts with the light-only, dark-only and unresolved tokens.

## Runtime overrides

Every public token is a custom property, so a selector can change it and the change cascades to that subtree. Override the token, not the component rule.

```css
.promo-card {
    --r-card-background: #fff8e1;
}

.theme-dark .promo-card {
    --r-card-background: #2a2410;
}
```

Private `--_r-*` tokens are internal. Overriding one may work today and break the next time the token layer rebuilds its scales; set the public token the component reads instead.

A theme-scoped override like the second rule is fine in application code. Rule 5 above is about the framework's own component partials, which must not branch on the theme apart from the two exceptions named there; an application setting a public token under a theme class is using the token layer as intended.

The framework uses the same mechanism internally. A component may reassign one of its own tokens in a narrower scope instead of duplicating the value: `.form-switch-large` sets `--r-form-switch-size` from `--r-form-switch-size-large`, the compact layout maps `--r-layout-sidebar-width` to the compact width, quick menu sizes step down in the small and x-small modifiers, and the layout header maps `--r-nav-link-color` to `--r-layout-header-nav-color`. These are overrides of existing tokens, not new tokens, so `TOKENS.md` does not list them separately.

## Naming conventions

- Palette primitives: `--r-color-{slot}`, `--r-color-{slot}-on` and `--r-color-{slot}-text`.
- Semantic roles: `--r-surface*`, `--r-text*`, `--r-border*` and `--r-link`, named for meaning rather than for a colour.
- Accent roles: `--r-{role}`, `--r-{role}-on` and `--r-{role}-text`.
- Component tokens: `--r-{component}-{property}`, for example `--r-card-background`, `--r-form-input-radius` or `--r-layout-header-height`. The property suffix says what the value holds: a colour or colour channel (`-color`, `-background`, `-background-color`, `-border-color`), a length (`-spacing`, `-padding`, `-size`, `-width`, `-height`, `-radius`), or an effect (`-shadow`, `-duration`, `-easing`, `-weight`).
- Framework-wide values: `--r-global-*` holds the base font, the font weights, the shared radius, the container width, and the page colour aliases.
- Internal values: `--_r-{name}`, only read by the token layer.

When a name is not obvious from these patterns, read [TOKENS.md](TOKENS.md) instead of guessing.

## Adding a token

- New palette slot: add the slot to `$colors` and its foreground pair to `$colors-on` in `_settings.scss`. `--r-color-{slot}`, `--r-color-{slot}-on` and the derived `--r-color-{slot}-text` appear automatically, and palette variant loops pick the slot up.
- New accent role: add the role to `$accent-roles` in `_settings.scss` and point it at an existing slot. The shared block emits the role's three tokens.
- New semantic role: derive it in `theme-roles()` in `_resolved.scss` from an existing seed or step, then register the role and its token in `$role-tokens` (public) or `$private-role-tokens` (internal) in `_token-registry.scss`. The build fails when a derived role is not registered.
- New component token that differs per theme: add the key to both the `light` and `dark` maps of `$theme-component-tokens` in `_token-registry.scss`, then read it as `var(--r-{key})`. The build fails when the two maps disagree.
- New component token declared once: add a `!default` setting under the component's group in `_settings.scss`, emit `--r-{key}: #{$setting}` in the shared block of `_css-variable.scss`, and read it as `var(--r-{key})`.

Run `npm run tokens` to refresh `TOKENS.md` and `npm run build` to verify the result.
